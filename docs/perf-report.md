# MiniDLC Performance Report

Measured on the development laptop: Intel i7-8550U (4 cores / 8 threads, AVX2 + FMA, 8 MB L3), Arch Linux, clang 23,
NumPy 2.5. The laptop's clock speed depends on its power state, so results vary by up to ~50% between runs; ranges are
given where that matters. Every number comes from a script in this repository, named with each table.

This report was rewritten after the 2026-10-17 audit, which withdrew several earlier claims (Section 9).

**What is being measured.** The MNIST `cpu` target runs **hand-written** LLVM IR kernels (`python/minidlc/llvm_engine.py`),
not code generated by the MiniDLC compiler, which is not yet connected to execution (see `docs/architecture.md`). The
numbers below characterise those kernels and the NumPy reference interpreter.

## 1. Hardware baseline

| Measurement | Value | Command |
|---|---|---|
| Single-core FP32 peak (AVX2 FMA microbenchmark) | 112–124 GFLOP/s | `build/dlc_fma_peak 1` |
| Four-thread FP32 peak | 206–448 GFLOP/s (power-limited laptop: short bursts reach full turbo, sustained load throttles) | `build/dlc_fma_peak 4` |
| Single-thread copy bandwidth (NumPy, 40 MB arrays) | 10–15 GB/s | `python3 benchmarks/stream_bw.py` |
| Ridge point (single-core peak ÷ copy bandwidth) | ~8 FLOP/byte | `python3 benchmarks/roofline.py` |

Caveats:
- The "triad" bandwidth printed by `stream_bw.py` (2.6–6 GB/s) is not a property of the hardware: NumPy evaluates
  `b + s·c` in two passes (five array streams plus a temporary) and the script divides by three. Use copy bandwidth.
- Bandwidth is single-threaded; this machine's multi-threaded DRAM bandwidth is higher.

## 2. Kernels against the CPU roofline

Command: `PYTHONPATH=python python3 benchmarks/roofline.py` (writes `docs/roofline_cpu.svg`). Latest run:

| Kernel | Intensity (FLOP/B) | Attained | Note |
|---|:---:|:---:|---|
| Hand-written fused matmul+bias+ReLU (128×784×256), 1 thread | 38.5 | 6.9 GFLOP/s (6% of single-core peak; 6.9–10.3 across runs) | Vectorized over output columns only |
| NumPy matmul+bias+ReLU, Arch system NumPy (netlib reference BLAS) | 27.6 | 3.6 GFLOP/s | Unoptimized BLAS |
| NumPy matmul+bias+ReLU, pip NumPy (OpenBLAS), 1 thread | 27.6 | 75–91 GFLOP/s | Context baseline (`benchmarks/fusion_ablation.py` in that environment) |
| Adam update (hand-written; vectorized by LLVM's loop vectorizer) | 0.46 | 18.0 GFLOP/s (38.8 GB/s) | 3.2 MB working set stays in L3 |
| ReLU (NumPy) | 0.25 | 6.4 GFLOP/s (25.6 GB/s) | 8 MB working set, mostly cache-resident |

Arithmetic intensities use a compulsory-traffic model (each operand read once, each result written once); they are not
measured DRAM traffic. The NumPy point on `docs/roofline_cpu.svg` uses the system (netlib) NumPy.

## 3. Epilogue fusion

Command: `PYTHONPATH=python python3 benchmarks/fusion_ablation.py`. Both variants use the same AVX2 GEMM loop nest; the
unfused one does the bias add and ReLU as separate passes.

| Variant | Time | Throughput |
|---|:---:|:---:|
| Bias + ReLU fused into the GEMM epilogue | 5.0–7.4 ms | 6.9–10.3 GFLOP/s |
| Bias + ReLU as separate passes | 5.0–7.4 ms | 6.9–10.3 GFLOP/s |
| **Speedup from fusion** | **0.99–1.00×** | |

Under the compulsory-traffic model, fusion removes two round trips of the 128 KB intermediate: 1,860.6 KB → 1,336.3 KB
(1.39× less traffic). At this size the intermediate stays in cache and the GEMM is ~99% of the work, so no speedup is
measurable. Fusion should pay off for memory-bound chains; P7 measures elementwise-chain fusion with generated kernels.

## 4. Memory planning

No figure is reported. The earlier one (1.64 → 1.21 MB, 26.2%) cannot be reproduced from any input in the repository,
and the v1 planner is unsafe: it computes liveness on the unfused op schedule, so a fused kernel's output is placed
inside its own inputs, and it lets intermediates reuse parameter buffers. (`dlc-opt --print-mem-report` reports 16.8%,
1.54 → 1.28 MB, on the MNIST forward graph, with the same defects.) Buffer assignment is rebuilt in P3 and re-measured on
the executed training graph.

## 5. MNIST MLP training

Model 784 → 256 → 10 with ReLU, cross-entropy, Adam (lr 1.5e-3), batch 128, 2 epochs (936 steps). Test accuracy is
measured on 9,984 of the 10,000 test images (the last partial batch is dropped).
Command: `PYTHONPATH=python python3 examples/mnist_mlp.py 2 [--target=reference]`.

| Run | Training time | Test accuracy |
|---|:---:|:---:|
| `--target=cpu`: hand-written LLVM IR kernels + NumPy softmax | 31.6 s | 96.88% |
| `--target=reference`, system NumPy (netlib BLAS) | 72.6 s | 96.93% |
| `--target=reference`, pip NumPy (OpenBLAS) | 13.6 s | 96.84% |

The `cpu` target is 2.3× faster than the interpreter on the netlib NumPy, and 2.3× slower than the same interpreter on a
standard NumPy.

Where the `cpu` step time goes (`examples/mnist_mlp.py 1 --target=cpu --profile`):

| Stage | Mean per step | Share |
|---|:---:|:---:|
| `bwd_layer1`: scalar `matmul_transA` for dW1, ReLU backward, bias gradient | 31.5 ms | 78.7% |
| `fwd_layer1_fused`: vectorized matmul+bias+ReLU | 6.6 ms | 16.5% |
| `opt_adam` (four parameter tensors) | 0.66 ms | 1.7% |
| `bwd_layer2` | 0.61 ms | 1.5% |
| `fwd_layer2_bias` | 0.43 ms | 1.1% |
| `softmax_loss` (NumPy) | 0.19 ms | 0.5% |
| `bwd_dlogits` (NumPy) | 0.03 ms | 0.1% |

The dW1 GEMM has the same FLOP count as the forward GEMM but is scalar with a strided inner loop, so vectorizing it is the
largest available speedup.

## 7. Character-level Transformer (reference interpreter)

Model: 2 pre-LayerNorm blocks, d_model 32, context 32, 30,656 parameters. Attention is single-head: `MultiHeadAttention`
does not split heads yet (fixed in P6). Data: TinyShakespeare, 1,115,394 characters, 65-character vocabulary.

| Run | Result | Command |
|---|---|---|
| 40-step demo, batch 4, Adam 8e-3 | Training loss 4.4626 → 3.1908 in 0.5 s (single-batch losses are noisy: 3.57 at step 35) | `examples/char_gpt.py` |
| 2,000 steps, batch 16, Adam 3e-3, 90/10 train/held-out split | **Held-out loss 2.1005 nats** after 101 s | `benchmarks/chargpt_heldout.py` |
| Unigram / bigram entropy of the text | 3.3128 / 2.4526 nats | printed by the same script |

Held-out loss by step: 0 → 4.1913 · 250 → 2.4953 · 500 → 2.3833 · 1,000 → 2.2296 · 1,500 → 2.1550 · 2,000 → 2.1005.

The 40-step demo ends near the unigram baseline: it has learned character frequencies, not context. The 2,000-step run
goes below the bigram baseline, so it uses context. Sample after 2,000 steps (temperature 0.8, prompt `ROMEO:`):
"Clord, dree thould a that us have teth to kreir fink, thes so eld halords, / Who here laut ilsch briver, With dime add
tho".

## 8. Correctness tests

| Suite | Count | What it checks |
|---|:---:|---|
| GoogleTest (`tests/unit`) | 21 enabled, 13 disabled | IR, passes, loop IR, runtime, CUDA template text. The disabled tests record known bugs |
| lit + FileCheck (`tests/lit`) | 11 (10 pass, 1 expected failure) | `dlc-opt` output after passes |
| Gradient checks | all 18 ops | Reference-interpreter VJPs vs float64 central differences |
| Contract tests | 9 | NaN/Inf, overflow, softmax axes, broadcasting, zero-size dims — on the reference interpreter only |
| Random-DAG fuzzer | 25 seeds | Reference VJPs vs finite differences (11 of the 25 graphs check a single input gradient) |

These tests cover the reference interpreter and the C++ passes in isolation. Nothing yet compares compiled code with the
reference; differential testing arrives with P4.

## 9. Withdrawn claims (2026-10-17 audit)

- **"2.27× faster than the reference interpreter"** (MNIST): measured against a netlib-BLAS NumPy (Section 5).
- **"2.63–2.77× kernel speedup from epilogue fusion":** compared the MiniDLC GEMM with a netlib-BLAS GEMM. Same-kernel
  fusion gives 1.00× (Section 3).
- **"26.2% peak memory reduction":** not reproducible, and the planner is unsafe (Section 4).
- **"LLVM ORC JIT", "ThreadPool multi-core dispatch", "32×64×32 tiling", "unroll ×4":** none is used on any executed path.
  The kernels are compiled by a `clang` subprocess and run single-threaded; the loop passes only set attributes.
- **GPU kernels plotted as operating points:** they were ceilings; no GPU code has run (Section 6).
- **Char-GPT "2 attention heads" and "loss drops monotonically from 4.33 to 3.15":** attention is single-head; that trace
  was not monotonic and not reproducible (unseeded initialisation, now fixed) (Section 7).
- **"All figures empirically measured without theoretical assumptions":** traffic and intensity figures use a
  compulsory-traffic model.
